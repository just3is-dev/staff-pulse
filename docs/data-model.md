# Модель данных

## Узел орг-структуры

`GET /api/org-tree` отдаёт плоский список узлов
(`@staff-pulse/shared`, `orgNodeSchema`): `id`, `name`, `parentId`,
`headcount`, `budget`, `performance`, `updatedAt`. `headcount` и `budget` —
собственные значения узла, без потомков.

`parseOrgTree` (`packages/shared/src/org-tree.ts`) проверяет форму списка и
структуру леса, прежде чем список используется где-либо ещё: `id` уникальны,
`parentId` либо `null` (корень), либо ссылается на существующий узел из того
же списка, циклов в цепочке родителей нет. Дальнейший код (построение
иерархии, агрегация) полагается на эти гарантии и не проверяет их повторно.

## Построение иерархии из плоского списка

`groupByParent` (`apps/web/src/org-model/org-tree-hierarchy.ts`) превращает
проверенный список в `Map<parentId, OrgNode[]>` — детей узла с данным
`parentId` (корни — под ключом `null`). Один проход по списку, без
сортировки: порядок соседей внутри массива — это порядок соседей в дереве,
как их вернул сервер, независимо от того, в каком порядке узлы шли во входном
списке (потомок может быть перечислен раньше родителя — `groupByParent`
не требует определённого порядка, каждый узел добавляется в список своего
родителя независимо от того, встречен ли уже сам родитель).

**Уровень (глубина)** узла не хранится в данных и не вычисляется этим
модулем — это позиция узла при обходе построенного дерева: у корня уровень 1,
у потомка — уровень родителя плюс 1. Текущий рендер дерева (`OrgTree`,
`OrgTreeNode`) уровень не использует — вложенность видна из вложенных
`<ul>`/`<li>`, без явного числа. Будущая таблица (SPEC-002) явно вычислит
уровень при обходе того же дерева для построения списка строк в порядке
дерева и для столбца «Уровень».

## Агрегация по поддереву

`aggregateSubtrees` (`apps/web/src/org-model/aggregate-subtrees.ts`) считает
для каждого узла показатели по нему самому и всем его потомкам:

- `headcount` — сумма `headcount` узла и потомков;
- `budget` — сумма `budget` узла и потомков;
- `performanceWeightedSum` — сумма `performance × headcount` узла и
  потомков;
- `averagePerformance` — `performanceWeightedSum / headcount`, средневзвешенная
  по `headcount` эффективность; `undefined`, если суммарная численность
  поддерева равна нулю (иначе было бы деление на ноль).

`performanceWeightedSum` хранится в результате, хотя таблице SPEC-002 нужен
только `averagePerformance` — это задел под этап 03: при точечном
пересчёте одного узла и его предков (без прогона по всему дереву) числитель
и знаменатель средневзвешенного значения нужно уметь корректировать
раздельно, а `averagePerformance` сам по себе для этого недостаточен (в нём
знаменатель уже потерян).

**Обход.** Функция обходит дерево от корней (`groupByParent(nodes).get(null)`)
рекурсивно в глубину: показатели узла — это его собственные `headcount`/
`budget`/`performance × headcount` плюс сумма уже посчитанных показателей
всех его детей (постфиксный обход — сначала потомки, потом узел). Каждый
узел агрегируется ровно один раз. Сложность — O(n) по числу узлов и O(n)
по памяти (по одной записи в результирующей `Map` на узел); глубина стека
рекурсии равна глубине дерева.

**Нулевая численность.** Если узел и все его потомки имеют `headcount: 0`,
`averagePerformance` для него — `undefined` («значения нет», см. AC-002-3 в
SPEC-002). Это не ошибка и не блокирует агрегацию предков: узел с нулевым
поддеревом добавляет к предку `headcount: 0`, `budget: 0` и
`performanceWeightedSum: 0` — на средневзвешенное значение предка это не
влияет (вклад нулевой), сам предок при этом получает корректное значение
`averagePerformance`, если его собственная численность или численность
других потомков ненулевая.
