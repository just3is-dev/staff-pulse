# ADR-003: Кэш запросов клиента — TanStack Query, а не собственный слой

Дата: 2026-09-14
Статус: accepted

## Контекст

Задание отдельно проверяет работу с API: кэширование ответов,
stale-while-revalidate со свежестью 5 секунд, отсутствие лишних запросов,
отмену запроса при размонтировании компонента. На этапе 03 к этому
добавятся live-патчи, которые применяются к данным в кэше без полного
перезапроса. Слой кэша можно написать самостоятельно или взять готовый.

## Решение

TanStack Query (`@tanstack/react-query` v5). Всё перечисленное в задании он
делает штатно: свежесть по времени, дедупликацию одновременных запросов по
ключу, отмену через `AbortSignal`, когда уходит последний подписчик,
structural sharing. Для этапа 03 у него есть точечная запись в кэш
(`setQueryData`). Настройки проекта собраны в одной фабрике —
`apps/web/src/api/query-client.ts`.

## Альтернативы

- **Собственный кэш** (Map + подписки + таймеры свежести) — показывает
  понимание механики, но это сотни строк с граничными случаями: гонки
  ревалидации, подсчёт подписчиков для отмены, сборка мусора. Их пришлось
  бы тестировать отдельно, а поведение, которого ждёт задание, уже есть
  готовым и проверено.
- **SWR** — та же модель stale-while-revalidate и точечная запись в кэш
  (`mutate`), но отмены запроса при размонтировании нет — её пришлось бы
  дописывать самим.
- **RTK Query** — тянет Redux Toolkit ради одного эндпоинта.

## Последствия

- Около 10 КБ gzip в бандле клиента при бюджете 200 КБ (замер сборки Vite:
  слой данных целиком — +16 КБ, из них около 6 КБ — проверка ответа на
  `zod/mini`).
- Поведение кэша проверяется тестами хука (AC-001-6…8), а не
  внутренностями библиотеки: обновление версии проверяется теми же
  тестами; при смене библиотеки поведенческие проверки сохраняются, но
  обвязку тестов (провайдер, фабрика клиента) придётся переписать.
- Отмена работает, только если функция запроса передаёт `signal` в
  `fetch` — это держит тест AC-001-8.
