# ADR-001: Общий пакет `packages/shared` отдаётся исходниками TypeScript, без шага сборки

Дата: 2026-09-14
Статус: accepted

## Контекст

Клиент (`apps/web`, Vite) проверяет ответ `GET /api/org-tree`, сервер
(`apps/server`, NestJS) этот ответ формирует. Тип узла и правила проверки
должны быть одни на обе стороны, иначе контракт API незаметно разъедется.
Приложения по-разному загружают модули: клиент собирает Vite (resolution
`bundler`), сервер компилирует `tsc` в `dist/` и исполняет JS в Node как ESM
(`module: nodenext`). По требованию CI гейты запускаются сразу после
`npm ci`, без отдельной сборки пакетов.

## Решение

Схемы и тип узла живут в workspace-пакете `@staff-pulse/shared`
(`packages/shared`), который экспортирует исходник `./src/index.ts` напрямую.

- Клиент: Vite, Vitest и `tsc -b` понимают `.ts` из связанного workspace-пакета
  без настройки.
- Сервер, проверка типов и сборка: в `apps/server/tsconfig.json` включены
  `preserveSymlinks` (файлы пакета видны через `node_modules` и считаются
  внешней библиотекой, поэтому `nest build` не кладёт их в `dist/` и не
  сдвигает его структуру) и `rewriteRelativeImportExtensions` (разрешает
  импорты с расширением `.ts` внутри пакета).
- Сервер, запуск: Node сам снимает типы с `.ts`-файлов пакета. Пакет
  подключён симлинком, Node разрешает его в реальный путь вне `node_modules`,
  где снятие типов разрешено. Поэтому исходники пакета пишутся только
  стираемым синтаксисом (`erasableSyntaxOnly`), а внутренние импорты — с
  расширением `.ts`.

Проверено: `nest build` кладёт в `dist/` только файлы сервера, а
`node dist/main.js` импортирует пакет и выполняет его код (Node 24). Загрузку
пакета настоящим Node держит тест `apps/server/src/shared-package.spec.ts`:
он запускает отдельный процесс Node, потому что Vitest снимает типы сам.

## Альтернативы

- **Копировать типы и схемы в каждое приложение** — нет единого источника
  истины, клиент и сервер расходятся без ошибки компиляции.
- **Собирать пакет в `dist/` (`tsc`) и экспортировать JS + `.d.ts`** — нужен
  шаг сборки после `npm ci` и при каждой правке пакета; устаревший `dist/`
  даёт ложно-зелёные проверки у зависящих приложений.
- **Nest monorepo library (`nest g library`) с бандлингом webpack** —
  привязывает общий код к инструментам Nest; клиенту всё равно нужен
  отдельный путь подключения.
- **Алиасы путей (`paths`) на исходники** — работают для проверки типов, но
  Node в рантайме их не разрешает; нужен отдельный загрузчик.

## Последствия

- Снятие типов включено в Node по умолчанию с 22.18, но фактический минимум
  проекта выше — `^22.22.3 || ^24.15.0 || >=26`: этого требуют devDependencies
  сервера (`@nestjs/schematics`, `@angular-devkit/*`). Зафиксировано в
  `engines` корневого `package.json`; `engine-strict` в `.npmrc` роняет
  `npm ci` на неподходящем Node сразу, а не при запуске сервера.
  Docker-образ (этап 04) должен удовлетворять тому же диапазону (проверено:
  на Node 22.12 импорт пакета падает с `ERR_UNKNOWN_FILE_EXTENSION`).
- В пакете нельзя использовать `enum`, `namespace` и другой нестираемый
  синтаксис; это ловит `tsc` пакета.
- `preserveSymlinks` у сервера влияет на разрешение всех зависимостей через
  симлинки. Сейчас симлинк один — сам `@staff-pulse/shared`.
- Правка пакета сразу видна обоим приложениям, пересборка не нужна.
