# ADR-004: Ревалидация неизменённых данных — ETag и явный условный запрос

Дата: 2026-09-15
Статус: accepted

## Контекст

Задание требует инвалидировать кэш только при реальном изменении данных, а
спека — чтобы ревалидация неизменённых данных проходила без повторной
передачи списка узлов, не меняла отображаемые данные и не сбрасывала дерево.
Через 5 секунд свежести клиент перезапрашивает `GET /api/org-tree`; нужно,
чтобы сервер мог ответить «не изменилось», а клиент — сохранить прежние
данные. Сервер работает на Express (под Nest), клиент — `fetch` через слой
кэша TanStack Query, в разработке запросы идут через прокси Vite.

## Решение

- **Сервер**: ETag, который Express ставит на ответ по умолчанию (слабый,
  по хэшу тела), и `304 Not Modified` без тела на совпадающий
  `If-None-Match`. Своего кода нет; поведение закреплено серверным тестом
  AC-001-3 — если ETag отключить, тест падает.
- **Клиент**: явный условный запрос. Данные кэша — снимок `{ nodes, etag }`,
  хук отдаёт компонентам только `nodes`. Функция запроса отправляет
  `If-None-Match` с ETag прежнего снимка и `cache: 'no-store'`; на 304
  возвращает прежний снимок тем же объектом, поэтому кэш не меняется и
  дерево не перерисовывается.
- Прокси Vite пропускает `ETag` и `If-None-Match` — проверено вручную
  (`curl` через `localhost:5173`: 304 с пустым телом).

## Альтернативы

- **Прозрачный HTTP-кэш браузера** — браузер сам отправит `If-None-Match` и
  на 304 отдаст `fetch` сохранённый ответ как 200. Кода меньше, но условность
  запроса не видна приложению и не проверяется тестом: в jsdom HTTP-кэша нет,
  а поведение зависит от заголовков кэширования и эвристик браузера.
- **Last-Modified / If-Modified-Since** — точность до секунды и привязка к
  времени, а не к содержимому; данные с тем же `updatedAt` могут отличаться.
- **Версия или хэш в теле ответа** — сервер всё равно передаёт тело целиком,
  экономится только перерисовка.
- **Сравнение данных на клиенте** — structural sharing TanStack Query уже
  сохраняет ссылки при равных данных, но трафик не экономится.

## Последствия

- `cache: 'no-store'` исключает двойное кэширование: единственный кэш
  клиента — TanStack Query.
- Если `fetch` вызван с `If-None-Match` из кода, спецификация Fetch отдаёт
  304 приложению, а не подменяет его сохранённым ответом — на этом держится
  клиентская ветка 304.
- Этап 03 (live-обновления): патч меняет данные на сервере, а с ними тело и
  ETag, поэтому ревалидация со старым ETag корректно получит 200 и полный
  список. Чтобы после применения патча на клиенте ревалидация снова давала
  304, снимок в кэше должен получать актуальный ETag вместе с патчем.
- Nginx (этап 04) должен не отбрасывать ETag при gzip: слабый ETag это
  допускает, но настройку нужно проверить.
