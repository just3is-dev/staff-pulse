# SPEC-001: Основа — mock API и интерактивное дерево орг-структуры

Статус: approved <!-- draft | approved | in-progress | done -->

## Зачем

Первый этап задания ([docs/assignment.md](../assignment.md), «01 FOUNDATION»).
Всё остальное — аналитическая таблица, live-обновления, production-сборка —
опирается на три вещи, которые появляются здесь: сервер с данными
орг-структуры, надёжная загрузка этих данных на клиенте и дерево, в котором
структуру можно просматривать. Отдельно задание требует экономно обращаться к
API: кэшировать ответы, не делать лишних запросов и сбрасывать кэш только
тогда, когда данные действительно изменились. Успех этапа — открыв приложение
одной командой, пользователь видит дерево подразделений с данными сервера,
а загрузка, ошибка и пустой ответ отображаются понятно.

## Что делаем

### Mock API

- Сервер отвечает на `GET /api/org-tree` плоским JSON-массивом узлов
  орг-структуры. Поля узла: `id`, `name`, `parentId`, `headcount`, `budget`,
  `performance` (0–100), `updatedAt`.
- Узлы образуют лес: у корневых узлов (дивизионов) `parentId` равен `null`,
  у остальных — `id` существующего узла. Уровень 1 — дивизионы, 2 — отделы,
  3 — команды; глубина не меньше трёх уровней.
- В наборе не меньше 40 узлов. Данные одинаковы от запроса к запросу
  (детерминированы) — на них можно опираться в тестах и на демонстрации.
- `headcount` — собственная численность узла без потомков, `budget` —
  собственный бюджет узла в рублях (целое число), `updatedAt` — момент
  последнего изменения узла в формате ISO 8601.
- На этом этапе данные сервера не меняются во время работы.

### Загрузка данных на клиенте

- Клиент запрашивает орг-структуру через слой кэширования. Данные считаются
  свежими 5 секунд после успешного ответа: в этот период повторное
  обращение к данным не порождает запроса к серверу.
- Когда свежесть истекла, при следующем обращении клиент сразу показывает
  данные из кэша и обновляет их фоном (stale-while-revalidate).
- Одновременные обращения к одним и тем же данным дают один запрос, а не
  несколько.
- Если данные на сервере не изменились, фоновая ревалидация не меняет
  отображаемые данные, не сбрасывает состояние дерева и завершается без
  повторной передачи списка узлов.
- Каждый ответ сервера проверяется на клиенте до использования:
  - форма — массив объектов с полями нужных типов, `performance` в
    диапазоне 0–100, `headcount` и `budget` — неотрицательные целые,
    `updatedAt` — валидная дата;
  - структура — `id` уникальны, каждый ненулевой `parentId` ссылается на
    существующий узел, циклов нет.

  Ответ, не прошедший любую из проверок, считается ошибкой, данные из него
  не показываются.
- Если компонент, которому нужны данные, исчезает со страницы до ответа
  сервера, запрос отменяется, а результат никуда не записывается.

### Состояния экрана

- **Загрузка** — пока нет ни одного ответа и нет данных в кэше.
- **Ошибка** — сеть недоступна, сервер вернул не-2xx или ответ не прошёл
  проверку. Показывается понятное сообщение и кнопка «Повторить».
- **Пусто** — сервер вернул пустой массив. Показывается сообщение, что
  подразделений нет.
- **Данные** — дерево. Если фоновая ревалидация завершилась ошибкой, дерево
  с прежними данными остаётся на экране, а рядом появляется ненавязчивое
  уведомление об ошибке обновления.

### Дерево

- Дерево показывает иерархию узлов. Ветви узлов с потомками раскрываются и
  скрываются по клику и с клавиатуры (Enter/Space на переключателе). У узла
  без потомков переключателя нет.
- При первом показе раскрыты узлы первого уровня, то есть второй уровень
  виден; узлы второго уровня и глубже свёрнуты.
- Каждый узел показывает `name`, `headcount` и цветовой индикатор
  `performance` из трёх диапазонов: 0–49 — низкая, 50–74 — средняя,
  75–100 — высокая. У индикатора есть текстовая альтернатива с числовым
  значением, так что информация не передаётся только цветом.
- Состояние раскрытия ветвей сохраняется при обновлении данных, пока узлы
  с теми же `id` существуют.

### Каркас проекта

- Клиент — Vite + React + TypeScript. Модули клиента импортируются от корня
  исходников (абсолютные импорты), без цепочек `../`.
- В клиенте нет inline-CSS: ни атрибутов `style` в разметке, ни
  `style`-пропсов в исходниках.
- Одна команда из корня репозитория запускает клиент и сервер в режиме
  разработки; открытый в браузере клиент показывает дерево с данными сервера.

## Границы

- Аналитическая таблица, агрегаты, сортировка и фильтр — этап 02 (SPEC-002).
  В дереве этого этапа `headcount` — собственная численность узла, а не
  сумма по потомкам.
- Изменение данных на сервере и live-обновления (WebSocket, SSE, поллинг),
  индикатор соединения, backoff — этап 03.
- Анимация раскрытия дерева и `prefers-reduced-motion` — этап 03.
- Полноценная клавиатурная навигация по дереву (стрелки между узлами,
  Home/End, роли ARIA tree) — не делаем; на этапе 03 навигация требуется
  только для таблицы.
- Автоматический повтор запросов при ошибке — не делаем; повтор — по кнопке.
- Выделение узла, поиск по дереву — не делаем на этом этапе.
- Docker, nginx, бюджет размера сборки, AI-поиск — этап 04.
- README, `docs/architecture.md`, `docs/data-model.md` — не в этой спеке;
  ADR на решения этого этапа пишутся здесь же, по мере принятия решений.

## Критерии приёмки

- [ ] AC-001-1: `GET /api/org-tree` отвечает 200 и JSON-массивом не меньше чем из 40 узлов, у каждого есть поля `id`, `name`, `parentId`, `headcount`, `budget`, `performance`, `updatedAt` нужных типов, `performance` в диапазоне 0–100.
- [ ] AC-001-2: В ответе `GET /api/org-tree` `id` уникальны, каждый ненулевой `parentId` ссылается на существующий узел, циклов нет, максимальная глубина не меньше 3; два последовательных запроса возвращают одинаковые данные.
- [ ] AC-001-3 (ждёт #11): Повторный запрос `GET /api/org-tree`, когда данные не менялись с предыдущего ответа, завершается без передачи списка узлов, а клиент продолжает показывать прежние данные.
- [ ] AC-001-4 (ждёт #8): Ответ, нарушающий форму (не массив; нет обязательного поля; поле неверного типа; `performance` вне 0–100; отрицательный `headcount` или `budget`; невалидный `updatedAt`), приводит к состоянию «Ошибка», данные из него не показываются.
- [ ] AC-001-5 (ждёт #8): Ответ, нарушающий структуру (повтор `id`; `parentId`, ссылающийся на несуществующий узел; цикл), приводит к состоянию «Ошибка», данные из него не показываются.
- [ ] AC-001-6 (ждёт #7): В течение 5 секунд после успешного ответа повторное обращение к данным не отправляет запрос к серверу; после 5 секунд обращение сразу отдаёт данные из кэша и отправляет ровно один фоновый запрос.
- [ ] AC-001-7 (ждёт #7): Два одновременных обращения к данным орг-структуры порождают один запрос к серверу.
- [ ] AC-001-8 (ждёт #7): Если компонент, запросивший данные, размонтируется до ответа сервера, запрос отменяется, а данные после размонтирования не записываются.
- [ ] AC-001-9 (ждёт #8): До первого ответа при пустом кэше показывается состояние «Загрузка»; при сетевой ошибке или не-2xx ответе — состояние «Ошибка» с кнопкой «Повторить», по нажатию которой запрос выполняется снова.
- [ ] AC-001-10 (ждёт #8): Пустой массив в ответе приводит к состоянию «Пусто» с сообщением, дерево не отображается.
- [ ] AC-001-11 (ждёт #10): Если фоновая ревалидация завершилась ошибкой, дерево с прежними данными остаётся на экране и показывается уведомление об ошибке обновления.
- [ ] AC-001-12: При первом показе дерева узлы первого уровня раскрыты, узлы второго уровня видны и свёрнуты, узлы третьего уровня не видны.
- [ ] AC-001-13: Клик по переключателю узла с потомками, а также Enter или Space при фокусе на нём, раскрывает свёрнутую ветвь и сворачивает раскрытую; у узла без потомков переключателя нет.
- [ ] AC-001-14: Каждый видимый узел показывает `name`, `headcount` и индикатор `performance`, цвет которого соответствует диапазону (0–49, 50–74, 75–100), а текстовая альтернатива содержит числовое значение.
- [ ] AC-001-15 (ждёт #10): После обновления данных, в которых сохранились узлы с теми же `id`, раскрытые пользователем ветви остаются раскрытыми, а свёрнутые — свёрнутыми.
- [ ] AC-001-16: Статическая проверка клиента падает на импорте с `../` и на inline-стилях (атрибут или проп `style`).
- [ ] AC-001-17 (ждёт #9): Одна команда из корня репозитория запускает клиент и сервер; клиент, открытый в браузере, показывает дерево с данными `GET /api/org-tree`.

## Переходные состояния

Спека вводит два правила статической проверки клиента (AC-001-16). Между
утверждением спеки и реализацией правила не действуют. При включении они
применяются к уже существующему коду клиента (сгенерированному create-vite):
если он нарушает правила, нарушения исправляются в той же задаче, что и
включает правило, а не отключением правила.

## Решённые вопросы

1. «Второй уровень открыт по умолчанию» трактуется как «второй уровень
   виден»: раскрыты узлы первого уровня, узлы второго уровня свёрнуты (AC-001-12).
2. Пороги индикатора `performance`: 0–49 — низкая, 50–74 — средняя,
   75–100 — высокая (AC-001-14).
